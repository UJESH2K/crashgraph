# crashgraph

**A rocket lander with no neural network. Everything it knows is a FalkorDB graph of its own attempts.**

Built for **Graph Hacks: Context for AI Agents** (WeMakeDevs × FalkorDB, Oct 15–18 2026).

**Tracks entered:** Agents That Act on Connected Data (primary) · Agent Memory and Coordination

---

## What it does

The lander starts knowing nothing and crashes. After every attempt it writes what happened into a FalkorDB graph; before every decision it reads that graph back. Over a few thousand attempts it learns to land, and because the knowledge is a graph rather than a weight matrix, you can ask it **why** any attempt crashed and get an answer you can check:

> Attempt 2997 crashed (score −217.8). Point of no return: "mid altitude, steady descent, far left of pad, drift left, upright" (89% of 36 past attempts through here failed). The decision that mattered came one step earlier at "high altitude, steady descent, far left of pad, drift left, upright", where it mostly chose left thruster. Attempts that landed from there mostly used main engine (57% of frames, 92 attempts). Best-known route to the pad from there has 6 more situations.

(Real output from our Luna run, generated by `explain_attempt`.)

Every number in that sentence is a Cypher query or a FalkorDB graph algorithm (shown in the UI next to the answer).

### The removal test (rule 3)

There is no model file, no Q-table on disk, no fallback policy. The pilot's only state between attempts is the graph. Wipe the graph (the "Wipe this world's memory" button) and the next attempt flails exactly like attempt 1. Restore a snapshot and it lands again.

## How the graph does the work

```
                       reads every frame                    writes after every attempt
   physics (Box2D) ──► Tile values ──► pick action ──► ... ──► tiles, situation path, outcome
```

| Memory type | In the graph | Used for |
|---|---|---|
| **Procedural** – how to act | `(:Tile {k, q:[4]})` – ~100k overlapping state tiles, each holding a value for the 4 engine actions | Every decision: the pilot fetches the 8 tiles covering its current state and fires the action with the highest summed value |
| **Semantic** – what tends to follow what | `(:Situation)-[:FLOWS {n, land, crash, cost}]->(:Situation)`, `(:Situation)-[:ENDED]->(:Outcome)` | Crash risk per situation, point of no return, safe-path search, PageRank danger hubs, failure families |
| **Episodic** – what happened | `(:Episode)-[:VISITED {i, frames, acts}]->(:Situation)`, `(:Episode)-[:NEXT]->(:Episode)` | Replays, "what did landing attempts do here", learning curve |

**One isolated graph per world** (`crashgraph_luna`, `crashgraph_ares`, `crashgraph_titan`) in one FalkorDB instance (multi-graph = per-tenant memory). Worlds differ in gravity, wind and turbulence. **Copy skills** shares procedural memory from one world's agent to another while their episodes stay separate.

### Graph data model

```
(:World {key, episodes, landed, crashed, seeded_from})

(:Tile {k, q:[coast, left, main, right], n})                  index on k

(:Situation {k, alt, vy, x, vx, tilt, legs, label,            index on k
             visits, crash_after, land_after})
(:Situation)-[:FLOWS {n, land, crash, cost}]->(:Situation)
(:Situation)-[:ENDED {n, cost}]->(:Outcome {name})

(:Episode {n, score, outcome, steps, fuel, epsilon,           index on n
           learned, gusts, ts})
(:Episode)-[:VISITED {i, frames, acts:[4]}]->(:Situation)
(:Episode)-[:RESULTED_IN]->(:Outcome)
(:Episode)-[:NEXT]->(:Episode)
```

Outcomes: `landed_pad`, `landed_off_pad`, `crashed`, `flew_off`, `timed_out`, `interrupted`.

### The queries the product depends on

**Decide (every frame)** — `crashgraph/memory.py`
```cypher
MATCH (t:Tile) WHERE t.k IN $keys RETURN t.k, t.q
```

**Learn (after every attempt)**
```cypher
UNWIND $rows AS r
MERGE (t:Tile {k:r.k}) ON CREATE SET t.q=[0.0,0.0,0.0,0.0], t.n=0
SET t.q=[i IN range(0,3) | t.q[i] + r.d[i]], t.n=t.n+1
```
```cypher
UNWIND $pairs AS p
MATCH (a:Situation {k:p.a}), (b:Situation {k:p.b})
MERGE (a)-[r:FLOWS]->(b) ON CREATE SET r.n=0, r.crash=0, r.land=0
SET r.n=r.n+1, r.crash=r.crash+$f, r.land=r.land+$s
```
```cypher
MATCH ()-[r:FLOWS]->() SET r.cost = -log((toFloat(r.land) + 0.5) / (toFloat(r.n) + 1.0))
```

**Explain** — `crashgraph/explain.py`
```cypher
// the path one attempt took, with crash risk at each step
MATCH (e:Episode {n:$n})-[v:VISITED]->(s:Situation)
RETURN v.i, s.label, s.visits, s.crash_after, s.land_after, v.acts ORDER BY v.i

// what landing attempts did in the same situation
MATCH (e:Episode)-[v:VISITED]->(s:Situation {k:$k})
WITH e.outcome IN ['landed_pad','landed_off_pad'] AS ok, collect(v.acts) AS acts
RETURN ok, size(acts), reduce(a=[0,0,0,0], x IN acts | [i IN range(0,3) | a[i] + x[i]])

// safest known route to the pad: weighted shortest path, edge cost = -log P(landing)
MATCH (a:Situation {k:$k}), (o:Outcome {name:'landed_pad'})
CALL algo.SPpaths({sourceNode:a, targetNode:o, relTypes:['FLOWS','ENDED'],
                   weightProp:'cost', maxLen:14, pathCount:1})
YIELD path, pathWeight
RETURN [x IN nodes(path) | coalesce(x.label, x.name)], pathWeight

// where attempts funnel into trouble
CALL algo.pageRank('Situation', 'FLOWS') YIELD node, score
RETURN node.label, score, node.visits, node.crash_after ORDER BY score DESC

// families of situations
CALL algo.labelPropagation({nodeLabels:['Situation'], relationshipTypes:['FLOWS']})
YIELD node, communityId RETURN communityId, count(node), sum(node.crash_after)
```

## The learning rule

Sarsa(λ) with tile coding (Sutton & Barto, *Reinforcement Learning: An Introduction*, ch. 9.5 and 12), with the value function stored as graph nodes instead of an array:

- The 6 continuous lander readings (position, velocity, tilt, spin) are covered by 8 offset grids. A state touches one tile per grid; an action's value is the sum of those 8 tiles.
- During an attempt the pilot keeps working memory: tiles fetched so far, eligibility traces, and unsaved changes. At the end it writes the changes to the graph in one batched `UNWIND`.
- Exploration starts at 50% random and decays with the number of attempts stored in the graph.
- Reward is Gymnasium LunarLander's built-in reward, unchanged.

## Run it

```bash
git clone <this repo> && cd crashgraph
python -m venv .venv && source .venv/bin/activate     # Python 3.12+
pip install -r requirements.txt                        # swig first if box2d fails: brew/apt install swig

python server.py            # control room at http://localhost:8000, embedded FalkorDB in ./data
```

On macOS/Linux there is no database to install: FalkorDBLite runs an embedded FalkorDB.

**Windows:** FalkorDBLite has no Windows build, so FalkorDB runs in Docker. Install Docker Desktop and double-click `run.bat` (it starts FalkorDB with the trained memory preloaded via `docker-compose.yml`, installs packages, and opens the control room).

To use Docker or FalkorDB Cloud on any OS:

```bash
docker run -p 6379:6379 -p 3000:3000 -it --rm falkordb/falkordb
FALKORDB_URL=redis://localhost:6379 python server.py
# FalkorDB Browser on http://localhost:3000 shows the same graphs live
```

Headless training (fast, no UI):

```bash
python train.py --world luna --episodes 3000 --exam 50
python train.py --world ares --episodes 1500 --seed-from luna   # transfer skills to a windy world
```

### Control room

- **Start / Pause / Resume** – the trainer process never stops; it idles between attempts.
- **Interrupt attempt** – ends the current attempt; what it saw is still written to the graph.
- **Gust ← / →** – shove the lander mid-flight and watch it recover (or not).
- **Watch / Fast / Train** – real time, ~5×, or full speed with the latest attempt replayed.
- **Exam mode** – no exploration and no learning: tests only what the graph already knows.
- **Snapshot / Restore / Wipe / Copy skills** – memory operations on the world's graph (`GRAPH.COPY`).
- **Attempt strip** – every attempt as a tick, red to green. Click one to replay it in 3D and see why it ended that way.

### MCP tools for LLM agents

`python mcp_server.py` exposes `memory_stats`, `explain_attempt`, `danger_hubs`, `crash_signatures`, `failure_families`, `learning_progress` and `read_cypher` (read-only via `GRAPH.RO_QUERY`). Example Claude Desktop config:

```json
{ "mcpServers": { "crashgraph": { "command": "python", "args": ["/path/to/crashgraph/mcp_server.py"],
  "env": { "FALKORDB_URL": "redis://localhost:6379" } } } }
```

### Optional photoreal view (Reactor)

The 3D view can be repainted live by [Reactor](https://www.reactor.inc)'s XMAX X2 real-time video-to-video model. Only the pixels of our own render go out; physics, learning and the graph never depend on it, and training never uses it.

```bash
pip install reactor-sdk pillow
REACTOR_API_KEY=... REACTOR_MAX_SECONDS=60 REACTOR_BUDGET_SECONDS=600 python server.py
```

Every session stops itself at `REACTOR_MAX_SECONDS`; total use is tracked in `data/reactor_usage.json` and blocked past `REACTOR_BUDGET_SECONDS`.

## Project layout

```
crashgraph/features.py     raw readings -> tile keys and situation keys
crashgraph/memory.py       every graph read/write (the only state the pilot has)
crashgraph/agent.py        the pilot: read tiles -> act; Sarsa(lambda) working memory -> flush
crashgraph/runner.py       one attempt, start to finish
crashgraph/explain.py      explanation queries and graph algorithms
crashgraph/trainer.py      long-running, steerable trainer
crashgraph/sim.py          Gymnasium LunarLander wrapper (world params, gusts, outcomes)
crashgraph/reactor_bridge.py  optional photoreal relay
server.py                  FastAPI + websockets control room
web/                       Three.js renderer and UI
mcp_server.py              MCP tools
train.py                   headless training
```
